# Работа с AI-агентами

Этот файл — одновременно инструкция для агентов, работающих в репозитории, и описание того, как он был сделан.

## Как устроен репозиторий (для агента)

- Монорепо на npm workspaces: `packages/shared` (чистая логика, без I/O), `packages/server` (Express + SQLite), `packages/web` (React).
- Любая логика воронки (видимость, прогресс, результат, валидация, резолв варианта) живёт **только** в `packages/shared` и используется клиентом, сервером и генератором. Не дублировать её в пакетах.
- Конфиг воронки — единственный источник правды про экраны. Во фронтенде не должно появляться знание о конкретных `step.id`.
- Сервер не доверяет клиенту: версия, вариант, UTM и `server_timestamp` берутся/ставятся на сервере.
- Схема БД: гибкие структуры — JSON-колонки. Новая версия конфига не должна требовать миграции.
- Перед коммитом: `npm test && npm run typecheck && npm run build`.
- Тесты сервера — через `createApp({ dbFile: ':memory:' })` + supertest. Не поднимать реальный порт в тестах.

## Как шла работа

### Декомпозиция

Задание разбито на слои с чёткими контрактами, чтобы части можно было делать и проверять независимо:

1. **Контракты** — `schema.ts` (zod-схема конфига), `events.ts`, `api.ts`. Сначала зафиксированы типы, потом реализация.
2. **Движок** — `conditions.ts`, `funnel.ts` + тесты. Самая «логичная» часть, покрыта тестами до появления сервера.
3. **Сервер** — отдельные сервисы `VersionService`, `SessionService`, `EventService`, `AnalyticsService`, каждый с явной ответственностью; `app.ts` только маршрутизация.
4. **Фронтенд** — `useSession` (восстановление/создание сессии), `tracker` (очередь событий), `FunnelPage` (рендер по конфигу), `/admin`, `/dashboard`.
5. **Генератор** — ходит по воронке теми же функциями shared, что и браузер, и сверяет ожидания с `/api/analytics`.

Приоритет по весам оценки: сначала пин версии, откат и идемпотентные события с тестами, потом UI.

### Что делалось параллельно

- Пока писались серверные тесты, независимо собирался фронтенд — у них общий контракт в `packages/shared/src/api.ts`.
- Генератор трафика и аналитика проектировались вместе: генератор печатает те же сегменты `версия × вариант`, что считает дашборд, поэтому расхождение видно сразу.

### Как проверялся сгенерированный код

- **Тесты как спецификация.** Пять обязательных тестов из задания написаны как отдельные `describe`-блоки; к ним добавлены кейсы на ловушки: дубль внутри пачки, non-array body, `rejected` среди `accepted`, событие из v3 для сессии v1, непоследовательный номер версии (`v9`), конверсия через условный шаг с нулём просмотров.
- **Ручная проверка в браузере** сценария из задания: ответить на `office_days`, вернуться, переключиться на `remote`. Проверялось и в UI (прогресс 3/4, результат `remote_async`/`remote_tool_sprawl`), и в БД (`answers_json` без `office_days`, в `events` нет значений ответов).
- **Сквозной прогон генератора** на чистой БД: 120 сессий, 2442 отправленных события, 436 дублей отбиты, 0 новых строк от повторной отправки пачек, цифры дашборда совпали с ожидаемыми точно.
- **Типы и сборка** после каждого крупного шага: `tsc --noEmit` по всем пакетам, `vite build`, `esbuild` сервера.
- Найденные и исправленные по ходу баги: черновик предыдущего шага «протекал» в поле следующего (исправлено хранением `stepId` и `draft` в одном состоянии); Enter в числовом поле не отправлял форму в embedded-браузере (явный `requestSubmit`); `@types/express` v5 не совпадали с express 4; бандл сервера не включал workspace-пакет.

### Что агенту НЕ делегировалось без проверки

- Формулы метрик и определение отвала — сверены вручную на маленьком наборе событий в тесте `analytics`.
- Семантика override при существующей сессии и прунинга ответов — продуктовые решения, описаны в README как допущения.
